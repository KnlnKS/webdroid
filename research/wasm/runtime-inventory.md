# Runtime inventory: what the JS-hosted VM provides, and what a Wasm-emitting VM would need instead

Scope: research only. Source read in `/Users/kunalan/Projects/webdroid-wasm` (branch `knlnks/bytecode-wasm`),
`src/jvm/*.ts` and `src/jvm/natives/{jlang,jthread,jsync,jreflect,jinvoke,jlambda,jthrowable,junsafe,jstring}.ts`,
plus the callers needed to understand them (`jentry.ts`, `jbox.ts`, `jvmruntime.ts`, `android/mainloop.ts`,
`android/handles.ts`, `native/jni.ts`). No browser was run and nothing was timed, so every performance statement
is either a measurement the repo already records (cited) or marked as a hypothesis. Items I could not verify
are tagged `[U#]` and listed in the last section.

Line numbers are for this worktree. "JS-specific" means the mechanism would not exist, or would look different,
on a VM that is not hosted in a JS engine.

## 0. Framing: the repo already rejected a Wasm backend once, and why that rejection is narrow

`docs/dex-performance-architecture.md:91-92` rejects "A Java Wasm backend: application time is object, Compose and
collection code with no eligible numeric bottleneck." That is an argument about *speed of compiled method bodies on
a V8 that JITs JS well*. It is silent on the things this inventory cares about: (a) BigInt `long`
(`:96-102`, Compose packed Offset/Constraints cost "about 40-65 ns per pack or probe, roughly 5-8% of Mihon
scrolling"), (b) the ceiling that the JS shape machinery puts on object layout (`bytecode-first-plan.md:397`,
"Stable object shapes"), (c) `new Function` code-cache limits (`bytecode-first-plan.md:310`), and (d) the
whole suspension protocol, which exists because JS has no stack switching. The inventory below is organised so
each of those can be judged separately.

Two axes decide most rows, so they are named once here and referred to by letter:

* **Heap axis.** (A) Wasm GC: Java objects are engine-managed `struct`/`array` values, GC is the engine's.
  (B) Linear-memory heap: Java objects are bytes in one or more `WebAssembly.Memory`, GC is ours (needs a
  shadow stack for roots), like TeaVM/Emscripten-style runtimes.
* **Suspension axis.** (J) JSPI: each Java thread is a `WebAssembly.promising` entry with its own engine-switched
  stack, blocking operations are `WebAssembly.Suspending` imports. (X) Exception-unwind frame capture, the
  current design transcribed to a Wasm exception tag. (C) CPS/asyncify-style rewrite.

Scale of the host surface that any option has to keep working (grep counts of text matches in non-test `src/`,
approximate `[U12]`): 81,610 lines of TS in `src/`, about 56,300 of them in `android/`, `jvm/natives/` and
`native/`; `vcall(` 759, `newObj(` 293, `scall(` 146, `driven(` 403, `mkThrowable(` 378, `registerJnis(` 153 plus
`registerJni(` 42, `rt.register(` 182, `setDeclared(` 79, `declaredField(` 69, `getDeclared(` 25,
`instanceof Promise` 69, `BigInt(` 313, `WeakRef` 32, `FinalizationRegistry` 10, `JObj` 1,341. Every one of these is
code that assumes a Java object is a JS object whose fields are JS properties and whose Java calls may return a
Promise.

## 1. Facility inventory

Verdict column: **ESSENTIAL** = the need is real for any implementation and only its form changes;
**ARTEFACT** = exists because the VM is hosted in JS; **MIXED** = both, stated. The last sentence of each
verdict says what would make it a non-blocker.

### 1.1 Data model

| Facility | How it works today (file:line, JS mechanism) | What a Wasm-emitting VM needs instead | Essential or artefact; what unblocks |
|---|---|---|---|
| Object layout, field access, hidden classes | A Java object is a JS class instance. Class ctor is generated by `new Function` with each field initialised to its default in declaration order (`runtime.ts:584-592`), extending the superclass ctor, so V8 hidden classes follow the Java hierarchy. Instance fields are properties named `f$name$hash(declaringClass)` (`abi.ts:59-61`), read as `v1.f$x$ab12` in emitted code (`compiler.ts:661-664`; cold form uses `[K[n]]` at `compiler.ts:308`). Plan wants stable shapes with only `$mon` added later (`bytecode-first-plan.md:397`). Native (TS) classes are hand-written JS classes extending `JObj` (`runtime.ts:29`); their field names are whatever the TS class used, mapped by `NativeSpec.fields` (`runtime.ts:48`, `:699-703`). Unknown fields on native classes are tolerated with a getter that throws or returns undefined (`runtime.ts:422-433`). | (A) one `struct` type per class, subtyping mirrors the Java superclass chain, fields at static indexes: `struct.get/set` with the type known at compile time. Header: vtable/class-descriptor ref plus identity-hash and lock words (see next rows). (B) fixed byte offsets, `i32.load`. Either way the field layout of every class an emitted method touches must be known when that method is emitted, and class shells must exist (not initialised) before the method body is generated. In (A) the type must be declared in the module that uses it (see row "Lazy compile, module granularity"). | Layout mechanism: ARTEFACT (hidden classes are V8's way of getting offsets; wasm gives them directly, probably faster, `[U7]`). That refactor is possible *before* any Wasm. |
| Object header: identity hash, monitor, class pointer | Class is `obj.constructor.$i` (`runtime.ts:96`, `:937`, `jlang.ts:19-22`). Identity hash is a lazily defined hidden own property `$ih` from an LCG counter (`abi.ts:268-277`); a string's identity hash is `String.hashCode` (`abi.ts:272`). Monitor is a lazily defined non-enumerable `$mon` (`monitor.ts:37-45`, `:18-23`), strings keyed by *value* in a `Map` (`monitor.ts:25`, `:42-44`). Compiled monitor sites load `$mon` and pass it to `R.me/R.mx` (`compiler.ts:574-575`, `runtime.ts:207-222`). | Header words in the object: class descriptor, `i32` hash (0 = unassigned), lock word or `ref null $Monitor`. Arrays need the same header, which a bare Wasm GC `array` cannot carry (see arrays). | Fields themselves: ESSENTIAL (ART has the same lock word + hash in the header). The `$mon` expando trick is ARTEFACT. Synchronising on strings by value is an ARTEFACT that also deviates from Java (two equal strings share a lock). Not a blocker: header words cost 8 bytes per object; thin-lock fast path can be wasm-resident (owner id + count in one `i32`), inflated monitors can stay JS-side. |
| Class statics | Statics are properties on the class constructor `s$name` (`abi.ts:63-65`, `runtime.ts:600-613`, instance `Ctor[prop]` at `compiler.ts:706-716`). Float/double statics are pre-seeded with `0.5` to keep V8 from going dictionary-mode (`runtime.ts:608-612`); after `<clinit>` the ctor is made a prototype to get fast properties back (`clinit.ts:10-18`, `:61`). Both need typed slots, and the statics holder must exist when the first method that references it is compiled. | ARTEFACT: the V8 dictionary-mode workarounds (`runtime.ts:608-612`, `clinit.ts:14-18`) vanish. ESSENTIAL: a statics home per class. Not a blocker. |
| `java.lang.String` as JS string | Strings are JS primitives, `String.prototype` is patched with ~hundreds of mangled Java methods (`jstring.ts:31-35`, `:55-64`), `definePublic` makes them non-enumerable (`suspend.ts:138-141`). `if-eq` on references is `===`, so string identity is *value* identity (`compiler.ts:644`; `compareTo` zero-only results compare natively `compiler.ts:763-764`, `prepared.ts:439-450`). `new-instance String` emits `""` and the later `<init>` call *replaces the register* with a freshly built string (`compiler.ts:593`, `:776-779`, `runtime.ts:1034-1062`). `iof` special-cases `typeof v === "string"` (`runtime.ts:934`). StringBuilder/Buffer are TS intrinsics over a JS string (`provenance.ts:57-58`). | Option 1: Java String = `externref` holding a JS string, with all hot operations as `wasm:js-string` builtins (`length`, `charCodeAt`, `concat`, `substring`, `equals`, `compare`, `fromCharCodeArray`, `intoCharCodeArray`) so there is no copy at the host boundary `[U6]`. ESSENTIAL: some string representation and a hashing strategy (JS strings cannot cache a hash; today `stringHash` is O(n) every call `abi.ts:279-283`). ARTEFACT: value identity for `==`, `""`-then-replace construction, by-value monitors, `typeof` checks. Most TS natives take and return JS strings (`rt.registerJnis` signatures), so Option 1 keeps host cost near zero and is the pragmatic default; Option 2 is only needed if in-wasm libcore String must be bit-exact. Neither blocks. |
| `long` as BigInt | `long` is a JS BigInt everywhere: arithmetic wrapped in `BigInt.asIntN(64, ...)` (`compiler.ts:837-838`, `:879-893`), `int-to-long` is `BigInt(x)` (`:840`), `long-to-int` is `Number(BigInt.asIntN(32,x))` (`:843`), shifts use a 64-entry preallocated BigInt table to avoid allocating the amount (`runtime.ts:1009-1012`, `compiler.ts:887-893`), `Unsafe` converts offsets through a `BigInt64Array` trick (`junsafe.ts:151-155`), handle ids are BigInts (`android/handles.ts`), 313 `BigInt(` calls in TS. The repo measured and rejected replacing it (`dex-performance-architecture.md:96-102`: two-int32 form "would touch every native"; asIntN wrapping gained 16% on a kernel). | `i64` locals and arithmetic natively; `i64.trunc_sat_*`, `i64.div_s` still need a divide-by-zero and `INT64_MIN / -1` guard (Wasm traps where Java does not; same for `i32.div_s`). At the JS boundary an `i64` import/export parameter *is* converted to/from a BigInt by the JS API, so host natives with `long` parameters still allocate a BigInt per call. | ARTEFACT inside compiled code (this is where Wasm wins outright, and it is the repo's own recorded 5-8% Compose cost). The *boundary* BigInt remains until the host ABI changes: handle-like longs (`handles.ts` indexes are small) can cross as `f64` or as an `i32` pair; general longs (timestamps, Unsafe addresses) can stay BigInt. Not a blocker. |
| `int`/`float`/`double`/`boolean`/`byte`/`char`/`short` | All are JS numbers; booleans are 0/1 (`abi.ts:3-6`). int arithmetic is `(a+b)\|0`, `Math.imul`, `(x<<24)>>24` for byte (`compiler.ts:835-878`, `:850-852`); `float` is `Math.fround` around every op (`:841`, `:894-898`); `div-int` guards zero explicitly and relies on `(x/y)\|0` for `INT_MIN / -1` (`:865-872`); `f2i/f2l` are explicit saturating helpers (`runtime.ts:992-1000`); cmpl/cmpg expanded to ternaries (`compiler.ts:638-643`). | Native `i32/i64/f32/f64`. `i32.trunc_sat_f32_s` / `i64.trunc_sat_f64_s` are exactly Java's `f2i/f2l` (NaN to 0, saturate), replacing `R.f2i/f2l`. `rem` for floats needs a helper (no `f32.rem`). `INT_MIN / -1` and `x / 0` need explicit branches (Wasm traps). Sub-int types: no native i8/i16 locals, so mask/sign-extend with `i32.extend8_s/16_s` and `& 0xffff`. | ESSENTIAL (semantics), mostly simpler than JS. The float-in-double-register hazards (`fround`, `0.5` seeding) are ARTEFACTS. Not a blocker. |

These carry no header: no hash, lock, or class pointer; identity hash and `synchronized(array)` need a side wrapper or a different layout (`struct {header, array}` costs an indirection per access). `array.copy` implements arraycopy in one instruction. No aliasing with linear memory: JNI `Get<Prim>ArrayElements`, Bitmap pixel arrays, direct ByteBuffers over native memory would copy or need an unsafe window. (B) arrays are bytes in linear memory with a header; aliasing with a guest `Memory` is natural only if they share a memory (multi-memory otherwise). | Mixed. ESSENTIAL: per-element-type arrays, bounds check, arraycopy. **The aliasing with guest memory is an ARTEFACT of typed arrays being views, but a real capability the repo uses** (non-movable arrays, Bitmap, `GetPrimitiveArrayCritical`); losing it is a perf and design cost in (A), not in (B). Not a blocker; it forces explicit copy-in/copy-out or a pinned-array API in JNI (which the JNI spec already permits). |

ESSENTIAL as a *compile-time typing* problem: this is the single largest new compiler analysis (see section 2). Unblocked by porting ART's verifier lattice (Zero, Const, Ref, Float, Long, Double) or R8/D8's `TypeAnalysis`; web-splitting makes the ambiguity per-web, and an ambiguous `const 0` web can be duplicated per use. |
| Boxes (`Integer`, `Long`, ...) and JS-number leakage | Boxes are real libcore objects with a `value` field (`jbox.ts:1-60`), the small-value caches come from libcore's own `*Cache` classes once initialised (`jbox.ts:34-52`). Boxes remain ordinary objects; `Integer.valueOf` stays bytecode. | ARTEFACT: the guessing exists only because JS numbers carry no Java type. Not a blocker; improves correctness. |
| `instance-of` / `check-cast` / type marks / inline caches | Linking marks the class prototype with `$I$<name>` = 1 for every assignable type (`runtime.ts:124`, `:637-641`) so a site is a property read; fallback is a 2-entry per-site cache keyed on `constructor`, then `R.iof` (`compiler.ts:576-589`, `runtime.ts:965-983`). The name-set representation is ARTEFACT. |

### 1.2 Code: decode, link, compile, tier, cache

| Facility | How it works today (file:line, JS-specific mechanism) | What a Wasm-emitting VM needs instead | Essential or artefact; what unblocks |
|---|---|---|---|
| DEX decode and CFG | `prepareMethod` decodes every instruction, finds block leaders from branch targets, try starts/ends and handler addresses, runs constant typing, `signOnly` marking and a `sync` (leaf) test (`prepared.ts:452-494`). Payload tables (`packed/sparse-switch`, `fill-array-data`) decoded on demand (`prepared.ts:149-163`, `compiler.ts:614-632`). | Same, plus full register typing and liveness (section 2). | ESSENTIAL; reusable almost as-is. |
| Control-flow structuring | `structure.ts` builds regions (entry, every handler, multi-entry blocks), orders them so loops are contiguous, and turns branches into labelled `break`/`continue`; a non-reducible CFG throws `"irreducible"` and the method falls back to a flat `for(;;) switch(pc)` (`structure.ts:1-5`, `:82-86`, `:227`; `compiler.ts:352-353`, `:415-416`, `:678-694`). For Wasm the analogue is "emit and instantiate cheaply" (baseline tier is fast to compile), or keep a small DEX interpreter written in Wasm/Zig (the repo already builds a Zig Wasm core: `src/native/core/*.zig`) for first-call execution. What the JS compiler consumes for a method (all from `PreparedMethod`, `prepared.ts:22-30`, and from the runtime at emit time):

What Wasm needs in addition (none of this exists today):

1. **A type for every register at every program point**: `i32`, `i64`, `f32`, `f64`, or reference. DEX does not give it. It must be inferred by a verifier-style forward dataflow (ART's lattice includes `Zero`, `Constant`, `ConstantLo/Hi`, `Boolean/Byte/Short/Char/Integer`, `Float`, `Long/Double` pairs, `Reference` with a class, `Conflict`). The existing `constantCarriers`/`typeConstants` pass (`prepared.ts:216-385`) is a degenerate version that only tracks "constants a float read can see", flow-insensitively for the null case; it is not sufficient. Consequences: (i) separate Wasm locals per register *web* where a register is reused with different kinds; (ii) `move` of an untyped constant to both an int use and a ref use needs duplication of the constant; (iii) `aget/aput` on untyped DEX need the array's element kind (currently erased by typed arrays); (iv) `if-eq` between two registers needs to know whether they are references or ints.
2. **A static class type for reference registers** if (A) struct types are used: `struct.get $Foo` requires the operand typed as (a subtype of) `$Foo`. ART's verifier provides the class of each reference register; where it is unresolved or merged to a supertype, emit `ref.cast`. At minimum: field owner class and method owner class are known from the instruction, so a cast at each use is always possible (cost `[U7]`).
3. **Per-method frame layout for suspension (X)**: a struct type with typed fields for every live local at each suspension site, or one per method sized to max registers by kind.
4. **Liveness** to limit what a suspension saves (JS saves all `regs` registers, `compiler.ts:446`).
5. **Linked layouts for every class named by the method** before emit: field index, vtable slot, interface selector, and statics holder index.
6. **Narrowing awareness**: `boolean/byte/short/char` stay `i32` in locals but need normalisation at defined points (`int-to-byte` etc. exist as DEX opcodes, but the verifier lattice distinguishes `Boolean/Byte/...` for `iput-boolean` truncation semantics).
7. **Exception-edge liveness**: values live into handlers must be in locals, which is natural in Wasm, but the `pc`-range catch walk (`compiler.ts:454-468`) needs a `pc` local updated at every try-covered instruction group, as today (`:370`).

## 3. What a from-scratch VM would not need (exists only because the VM is hosted in JS)

* Name mangling of methods and fields (`abi.ts:11-65`, `frameName` `:254-266`): vtable slots, field indices, method ids.
* Two calling conventions, `SUSPENDED` sentinel, `toPublic/toJava` adapter closures (`suspend.ts:96-136`) and the `javaFace/publicFace` wrappers on every host method (`runtime.ts:259-263`, `:678`).
* Promise-return protocol: `instanceof Promise` checks at call sites (`compiler.ts:520-528`), `after`, `shareable`, `once`, `suspendWith` single-microtask unwinding (`suspend.ts:39-94`).
* `driven()` generator natives (403 sites) if natives become wasm or follow a trampoline rule.
* Hidden-class workarounds: `dictionaryMode` (`runtime.ts:90-91`, `:595`), `0.5` static seeding (`:608-612`), `fastStatics` (`clinit.ts:10-18`), `$ih`/`$mon` expandos (`abi.ts:275`, `monitor.ts:40`), `directName` for inlining (`abi.ts:51`), megamorphism avoidance in `Runtime.me` (`runtime.ts:204-206`), BigInt shift tables (`:1009-1012`), `shortStringUnits` scratch arrays (`abi.ts:139-160`).
* `new Function` eval and its limits: per-class `new Function` at link (`runtime.ts:570`, `:591-592`), `compileClass` (`compiler.ts:61`), cold handler pool (`cold.ts:49`), `bodyScript` (`codecache.ts:35`), code cache via Cache Storage scripts, classic-script import to avoid module retention (`aot.ts:55-79`), line-number maps for stack frames in persisted chunks (`codecache.ts:44-52`, `:117-126`), `retarget`/cells for V8 inlining (`tiering.ts:19-36`).
* Cold interpreter of pooled handlers and OSR transfer from cold frames (`cold.ts`, `tiering.ts:186-193`), unless Wasm module cost forces a first-call tier anyway.
* Idle-callback compile budgeting for JS parse cost (`tiering.ts:45-88`) and the retained-source cap (`:46`).
* Value-model glue: `null`/`0` runtime normalisation (`compiler.ts:295-296`, `:910`), "bare number guessing" boxes (`jbox.ts:80-83`), `iof` special cases for `typeof string/number/bigint` (`runtime.ts:934-935`), `describeVal` for raw (`:1109-1114`), `STRING_TYPES/BOX_UNIVERSE` (`:1116-1119`).

* Dev-time "compile is not running" caveats (profiles compile ahead, `runtime.ts:419-421`).

## 4. Things a Wasm VM newly has to build

1. **A type system for Java inside Wasm**: class descriptors, subtype display, interface tables/IMT, array element classes, and the mapping from Java classes to Wasm struct types (only (A)). Decide how classes defined in later modules reuse already-declared types (rec-group canonicalisation `[U4]`) or avoid the issue by using one generic object struct plus typed accessors.
2. **Register type inference / mini-verifier** (section 2), including web splitting and `ref.cast` placement. This is the biggest compiler addition and a source of subtle bugs; it should be validated against ART's verifier outputs on the 32k-class `framework.jar` smoke (`bun run smoke`).
3. **Dynamic code publication**: shared function table(s), module-per-class (or chunk) emission, trampolines per signature shape for lazy compile, a policy for what to compile eagerly; a runtime that can instantiate modules cheaply and handle compile failure per method (today `unimplementedMethod` makes one bad method throw at call, `compiler.ts:228-234`).
4. **Suspension substrate**: either JSPI integration (promising entries per thread, Suspending imports, a restructure of all TS natives that re-enter Java so no JS frame lies between), or the exception-unwind frame-capture scheme with typed frame structs and a flat resumable twin per method.
5. **Exception design**: one Java-throwable tag (payload: Throwable reference), possibly a second internal tag for suspension (X); catch-by-class dispatch; explicit null/bounds/divide/overflow checks; `StackOverflowError` by depth counter; `OutOfMemoryError` by budget; conversion at every JS boundary of `WebAssembly.RuntimeError`, `WebAssembly.Exception` and `RangeError`.
6. **Stack walking**: a way to produce `StackTraceElement[]` (and `getStackClass`, caller-sensitive `Reflection.getCallerClass`, `getClosestUserClassLoader`: `jthrowable.ts:109-121`), via `Error.stack` + name section + offset-to-pc tables, or a shadow stack. Today's `frameOf` regex parsing of function names (`abi.ts:261-266`) and marker comments (`stacklines.ts:17-29`) need replacements.
7. **Field/method accessor generation for reflection, Unsafe, VarHandle, JNI, `clone`**: generated accessor funcs (or tables) keyed by field/method id; a generic argument marshalling layer from boxed Object[] to typed parameters per signature shape.
8. **Runtime class creation** for Proxy, annotation instances, host lambdas and helper classes, without compiling each method.
9. **Strings**: the `wasm:js-string` import set (or own String), hashing, `equals/compareTo` fast paths, `StringBuilder` (the TS intrinsic is a JS string `+=`, `provenance.ts:57`), interning (`const-string` identity), and conversion functions to/from `byte[]`/`char[]` (`R.newStr` table, `runtime.ts:1034-1062`).
10. **Weak reference and finalization bridge** for Java objects (JS `WeakRef`/`FinalizationRegistry` on wasm refs, `[U2]`), plus replacement of `claimOnStore` and `NativeAllocationRegistry` hooks.
11. **A GC budget/accounting layer** (OOM, `Runtime.totalMemory/freeMemory`).
12. **Heap/boot-image story**: a way to preinitialise platform statics at build time (B: snapshot bytes; A: replay or global initialisers; neither exists today).
13. **Host ABI for `long` and handles**: a convention to avoid per-call BigInt allocation (`handles.ts` ids as `f64`/`i32` pair) in the ~195 JNI natives.
14. **Instrumentation hooks in the emitter** replacing `jsrc`/`trace`/profile source hooks (`compiler.ts:429-433`, `scripts/trace.ts`).
15. **A test/validation story**: wasm validation of every emitted method in `bun run smoke` (compile all 32,713 `framework.jar` classes with 0 failures, `bytecode-first-plan.md:§1`), differential fuzz of arithmetic corner cases (`INT_MIN/-1`, float to int, shifts), and an interpreter-vs-JIT agreement check like the ARM core's.

## 5. Design implications worth stating plainly

* **The runtime gains from Wasm are concentrated in three places**: `long` arithmetic, object field access and dispatch without hidden-class fragility, and removal of the `new Function`/code-cache constraints. They are not in the Promise/suspension machinery, which gets harder, not easier, unless JSPI is accepted.
* **The cost is concentrated in the host surface**, not in the compiler: the ~80k lines of TS assume Java objects are JS objects and that any Java call may return a Promise. A staged path that does not need Wasm first is to (1) funnel every Java-field access in TS through `getDeclared/setDeclared`-style helpers, (2) bound the set of TS natives that call back into Java (`vcall` 759, `driven` 403) behind explicit "call and maybe wait" helpers (`after`, `scall`) so they can later become trampolines, (3) move `long` handles to an ABI that avoids BigInt (`handles.ts`), (4) typed host signatures so no value is guessed (`jbox.ts:80-83`). All four make the JS VM better or neutral and are prerequisites for any Wasm backend.
* **Two features the JS VM has that the Wasm GC design (A) loses unless engineered**: zero-copy aliasing of `byte[]` with native memory (`jnio.ts:129-136`) and heap-image snapshots for the boot image (§4.3 is open work already). Design (B) keeps both and adds shared-memory threads, at the price of writing a precise GC with a shadow stack.
* **Behaviours the current VM does *not* implement, so a Wasm VM need not match them initially**: `ArrayStoreException`, finalizers, soft-reference clearing, `System.gc`, other threads' stack traces, `LambdaMetafactory`/`const-method-handle`, access checks in `MethodHandles.Lookup` (`jinvoke.ts:210`), distinct memory orders for VarHandle modes (`:136`), string reference identity.
* **Exceptions are cheap to keep structurally** (Wasm EH ↔ JS catch) but need an explicit-check discipline that is a global change in how the emitter handles `iget`, `invoke`, `aget`, `div`.
